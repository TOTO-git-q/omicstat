# Method basis

Locked environment: limma 3.68.5, Bioconductor 3.23. Source: `acceptance/exemplars/limma-camera/L1_bioc3.23/limma/` (`Rd/camera.Rd`, `Rd/fry.Rd`, `Rd/roast.Rd`, `Rd/mroast.Rd`, User's Guide §18.1.10). Frozen owner decisions: `acceptance/exemplars/limma-camera/PACK.md` S1 P-1 through P-3.

A competitive question uses camera on continuous expression, or cameraPR when only ranked statistics exist. A self-contained question uses the one chosen fry, roast or mroast test. The suite never compares their significance to choose a method. The camera correlation 0.01 is fixed, not estimated. A fixed correlation gives consistent inflation across sets but can rank or calibrate sets differently from estimating correlation set by set.

The offline Yoruba F10/F11 files are SHA-256 checked. The guide's printed camera anchor is Y 13 Up P=2.40e-262 FDR=4.80e-262, X 54 Down P=5.58e-26 (usersguide.rendered.txt:7497-7500). Root cause of the earlier mismatch (docs/build/S4_ANCHOR_TRACE.md): limma 3.66.0 changed the default of `voom(adaptive.span)` to TRUE (L1 `NEWS.txt`, version 3.66.0); the static guide was printed with the old fixed span 0.5. The smoke test runs the guide's own code with `voom(..., adaptive.span = FALSE)` written out and reproduces every printed value (camera Y P 2.402131e-262, FDR 4.804263e-262; X P 5.576931e-26; consensus correlations 0.4455442 / 0.4459984 = printed 0.446); the module run on that guide-era voom E + weights gives the same camera row (PRINTED anchor, version-matched).

The frozen suite route is unchanged: upstream voom keeps the locked 3.68.5 default `adaptive.span = TRUE`, which gives Y P=1.79122449658387e-262, X P=6.02018304198957e-26 (consensus correlation 0.4454514); this is asserted separately as a REPLAY anchor (engine = independent direct camera call). Whether the suite should state or change the voom span is an owner item, not decided here. Guide mroast anchor at 9999 rotations is Y/X P=1e-04 and matches.

Input contracts (S4): a limma-voom / limma-array / limma-dupcor run is consumed through its EList (E + observation weights), fitted design and tested coefficient, unchanged; flags that would rebuild a different design are refused. A limma-dupcor upstream carries a block: fry/roast/mroast use its block and consensus correlation; camera has no block argument and runs only with `--acknowledge-block-ignored` (QC LC-06), as the guide's 18.1.10 camera call does. cameraPR consumes the ranked_list metadata (metric, contrast, positive end) and refuses flags that would override it. Batch-corrected objects or a corrected lineage are refused (`OS_BATCH_CORRECTED_INPUT`).

Figures: gene-set bar (all routes), barcode plot with the relative-enrichment worm (limma barcodeplot's tricubeMovingAverage, span 0.45) for the top two sets, and an MD plot with those sets highlighted (expression routes only; the statistic is the upstream fit's moderated t or a display-only lmFit/eBayes on the same design, weights and block; never used by a test).
